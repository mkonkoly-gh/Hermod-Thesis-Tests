# Pi5 production campaign

The campaign measures Hermod against the production target — an 8 GB
Raspberry Pi 5 running Ubuntu Server 24.04 LTS arm64 with MicroK8s —
across 66 profile runs grouped into ten phases. Every run is described
by a frozen YAML profile under `profiles/`; the orchestrator hashes
`plan.yaml` and refuses to mix data across plan revisions.

Per-run output lands under `raw/<UTC-timestamp>-<profile>-<phase>/`
(load-generator JSON, Prometheus scrapes, per-minute pod sampler,
and a phase-specific `issues.md` where applicable). The `state/`
files in this doc are derived; the canonical artefacts live in `raw/`.

## Phase layout

| Phase | Profile family | Purpose |

## Notable incidents (chronological, mid-campaign)

### 4k baseline saturates at coordinator CPU

Across the four baseline rates: 500, 1k, 2k delivered zero drops with
sub-ms p99; **4k showed 15.8 % loss** with the coord pod at 994 m of
its 1-core cap and the ingest channel overflowing under DropOldest.
Confirmed by V as **expected saturation, not a regression**: the
system is designed for 1k msg/s nominal, the dashboard's anomaly
detector gates `drops bad` on `target < 4000`, and 4k+ runs exist to
characterise the saturation curve (RQ1, RQ10) and graceful degradation
(H-tight, H-breaking).

Thesis claim mapping:

- ≤ 2k: zero drops, p99 sub-ms — RQ1 baseline calibration
- 4k: graceful degradation — RQ10
- 6k+: explicit overflow → DropOldest works — RQ7 safety

### Feature-flag matrix cost signatures (RQ4/5/6/12)

After fixing the `Hermod__` env-prefix bug in the runner, the B-* runs
produced clean differentiated signatures:

| Run | CPU avg | Drops | Comparison |
|---|---|---|---|
| A-baseline-2k | 403 m | 0 | reference |
| B-no-cache-2k | 1 126 m | 280 951 | 2.8× CPU vs baseline; saturation kicks in at 2k vs 4k for baseline. Cache benefit ≈ 2.8–3× |
| A-baseline-4k | 607 m | 220 | reference @ saturation |
| B-no-cache-4k | 1 160 m | 580 693 | 1.9× CPU; loses ~half of inbound vs baseline's negligible drop |

These two B-no-cache anomalies (drops at 2k, CPU at ceiling at 4k) are
the **expected cost-of-disabling-cache signal**, not regressions. The
analyser flags them automatically; they map to RQ4/5/6 (feature-flag
cost matrix) and RQ12 (operating envelope).

Other clean separations from the B-* matrix:

- `debug-log-2k`: 557 m vs baseline ~320 m — debug logging adds CPU
- `no-rollup` / `no-msg-persistence` / `no-device-state` at 2k:
  309–374 m, slightly under baseline (fewer writes)
- `engine-seq-4k` vs `engine-par2-4k`: par2 p99 = 1.94 ms > seq p99 =
  0.99 ms while par2 cpu_avg = 607 m < seq 677 m. **At 4k the run-pair
  behaves opposite to the parallelism-helps assumption** — likely lock
  contention in the parallel scheduler at this rate. `engine-par4` and
  `engine-par8` clarify the curve; the trend is preserved.

### 5 mid-campaign failures — root-caused and fixed

`B-storage-noop-{2k,4k}-flat` and `C-trace-{500,2k,4k}` failed during
the run with `rule seed mismatch: expected 1200, found 0` and
`profile error: unknown run keys: ['env']` respectively.

Root causes:

1. `profiles/_loader.py:_validate_run` allowed only `{warmup_sec,
   measure_sec, cooldown_sec, repeats}`. The `trace-baseline-...yaml`
   declares `run.env.HERMOD_UUID_TRACE_ENABLED: "true"` — schema
   rejected at resolve time.
2. `scripts/run-profile-pi.sh` rule-seed step counted rows in the
   `rules` table; with `storage_mode=Noop` every write is a no-op so
   `count(*)` is 0 by design — false-positive failure.

Fixes:

- `_loader.py`: added `env` to allowed `run` keys plus value validation.
- `run-profile-pi.sh`: appends `run.env` entries to the
  `kubectl set env` arg list, and skips `count(*) FROM rules` when
  `storage_mode=Noop`.

The 5 failed runs were re-queued automatically by the orchestrator's
`failed → queued` transition on relaunch; all eventually passed on
retry with `attempts++`.

**E-pgbench rerouting:** the `pgbench-only` namespace
has only Postgres — no NanoMQ, no coord. The `storage-pgbench` profile
expected a custom `run-isolation-pgbench.sh` harness, but `run-one.sh`
always invokes the load_gen path. With no broker, load_gen errored on
connect and wrote a Python traceback into `loadgen-r1.json`; the run
was marked passed (rc=0) with bogus zero-counter data. The bogus raw
dir was archived; E-pgbench was rerouted to overlay `coord-only` /
profile `baseline-pi5-live-8gb`. E-pgbench therefore measures coord
throughput in coord-only at baseline rate (same shape as A-baseline-*
but with the E phase tag). The actual postgres write-throughput
question is answered by D-soak (sustained ρ=0.9 over 27 min) and the
storage-noop / no-msg-persistence comparison triplet.
